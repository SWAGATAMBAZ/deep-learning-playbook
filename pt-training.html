nn.Module: the building block

🧒 In plain English

A Module is a Python class with two jobs. __init__ creates the layers (and their learnable weights), and forward says how data flows through them. Assign a layer as an attribute and PyTorch automatically tracks its parameters, moves them with .to(device), saves them in state_dict and hands them to the optimizer.

ContainerUse when
nn.SequentialA straight pipeline with no branching
nn.ModuleListA variable number of layers you loop over. A plain Python list would hide them from .parameters(), so they wouldn't train.
nn.ModuleDictNamed sub-modules, e.g. one embedding per categorical column or one head per task
torch.nn.functional (F)Stateless ops (relu, softmax, cross_entropy). Use modules when there are weights or train/eval behaviour (Dropout, BatchNorm).

Saving and loading

⚠️ Saving pitfalls

torch.save(model) pickles the class path and breaks when you refactor; save the state_dict. Load with map_location to move GPU checkpoints to CPU. A model wrapped in DDP or torch.compile has prefixed keys (module., _orig_mod.); save the unwrapped model's state_dict. Use weights_only=True for files you didn't create.

Dataset and DataLoader

🧒 In plain English

A Dataset answers two questions: how many samples (__len__) and give me sample i (__getitem__). A DataLoader shuffles, batches, and loads in parallel worker processes so the GPU never waits for data.

The complete training loop (memorise this structure)

🎯 The 7 lines interviewers look for

model.train() · move the batch to the device · opt.zero_grad() · forward + loss · loss.backward() · (clip) · opt.step(). Then model.eval() + torch.no_grad() for validation. Missing eval() or zero_grad() is the most common red flag.

Reproducibility

Even with seeds, results vary across GPUs and library versions. Report mean ± std over 3–5 seeds when comparing models; a 0.3% "win" from one seed is noise.

Interview Q&A

Why use nn.ModuleList instead of a Python list?

Modules in a plain list aren't registered as sub-modules, so their parameters are missing from model.parameters() (never trained), state_dict (never saved) and .to(device) (stay on the CPU).

Parameter vs buffer?

Both are saved in state_dict and moved with the model. Parameters are learnable (returned by .parameters() and updated by the optimizer). Buffers are state that isn't trained, like BatchNorm running mean/var or a positional-encoding table.

What does model.eval() change?

It sets training=False on every sub-module, so Dropout stops dropping and BatchNorm uses running statistics instead of batch statistics. It does not disable gradient tracking; use torch.no_grad()/inference_mode() for that.

Your GPU utilisation is 30% during training. Why?

Usually a data bottleneck: too few num_workers, heavy CPU augmentation, slow disk, no pin_memory, or tiny batches. Other causes: .item()/.cpu() calls every step forcing synchronisation, and Python overhead. Profile first (see PyTorch III).

How do you implement gradient accumulation?

Divide the loss by the number of accumulation steps k, call backward every micro-batch, and only call opt.step() + zero_grad() every k micro-batches. The effective batch is k × micro-batch. BatchNorm still sees micro-batches.

How would you handle a 1:100 class imbalance in the DataLoader?

Either a WeightedRandomSampler (balanced batches), or keep natural sampling and use pos_weight / focal loss. Don't do both at full strength, because you'd over-correct. Re-calibrate probabilities afterwards if you resample.

Where do you call scheduler.step()?

After optimizer.step(). Per batch for OneCycle/warm-up schedules defined in steps, per epoch for epoch-based ones like StepLR. ReduceLROnPlateau takes the validation metric: sched.step(val_loss).
