Training & improving model performance

Knowing the architectures is the easy part. What interviewers really probe is whether you can make a model train and generalise: pick the learning rate, spot overfitting, handle imbalance, and debug a flat loss curve.

📐 Adam in three lines
m ← β₁m + (1−β₁)g    v ← β₂v + (1−β₂)g²    w ← w − η · m̂ / (√v̂ + ε)

m = running average of gradients (direction, i.e. momentum). v = running average of squared gradients (how noisy or large a weight's gradients are). Dividing by √v gives rarely-updated weights bigger steps, which is great for sparse features like embeddings. Defaults: β₁=0.9, β₂=0.999.

Learning rate: the single most important hyperparameter

🧒 In plain English

If you can tune only one thing, tune the learning rate. Too high and the loss explodes or goes NaN. Too low and the loss decreases painfully slowly and gets stuck. The usual trick is to start with a short warm-up (small steps while the weights are random), go big, then decay to fine steps near the end.

  • LR range test: increase the LR exponentially over one epoch, plot loss against LR, and pick roughly 1/10 of the LR where the loss is lowest.
  • Schedules: step decay, cosine annealing (the most common today), OneCycle, and linear warm-up then decay (the standard for transformers).
  • ReduceLROnPlateau: cut the LR by 10× when validation loss stalls. A simple and robust choice.
  • Batch size link: if you double the batch size, you can roughly scale the LR up too (the linear scaling rule, used with warm-up).

Weight initialisation

The goal is to keep the variance of activations (and gradients) roughly constant from layer to layer, so signals neither die nor explode.

Xavier / Glorot

Var(w) = 2 / (fan_in + fan_out). For tanh/sigmoid.

He / Kaiming

Var(w) = 2 / fan_in. For ReLU; the 2 compensates for ReLU zeroing half the inputs. PyTorch's default for Linear/Conv layers is close to this.

Normalisation layers

🧒 In plain English

As earlier layers learn, the inputs to later layers keep shifting in scale, so every layer is chasing a moving target. Normalisation re-centres and re-scales each layer's inputs so training is faster and more stable, and you can use a higher LR.

⚠️ Classic bug

Forgetting model.eval() at inference. BatchNorm then uses the current batch's statistics instead of the running averages, and dropout stays switched on. Predictions become noisy and change with batch composition.

Regularisation: stopping memorisation

01

Dropout

Randomly zero p% of neurons during training (p = 0.1–0.5). The network can't rely on any single neuron, so it works like averaging many thinner networks. Turned off at eval.

02

Weight decay (L2)

Penalises large weights, so the model learns smoother functions. Use AdamW with wd = 0.01–0.1.

03

Early stopping

Track validation loss, keep the best checkpoint, and stop after N epochs with no improvement.

04

Data augmentation

Images: flip, crop, colour jitter, MixUp/CutMix. Text: back-translation, synonym swap. Tabular: noise, SMOTE (use carefully).

05

Label smoothing

Train on 0.9/0.1 targets instead of 1/0. Stops over-confidence and improves calibration.

06

Smaller model / more data

Still the most reliable fixes. Transfer learning counts as "more data".

Class imbalance (fraud, default, churn)

🧒 In plain English

If 0.2% of transactions are fraud, a model that always says "not fraud" is 99.8% accurate and completely useless. You have to make the rare class matter more, and measure with metrics that notice the rare class.

  1. Metrics first: PR-AUC, recall at a fixed precision, F1, and expected cost. Never just accuracy. ROC-AUC can look great even under heavy imbalance.
  2. Weighted loss: BCEWithLogitsLoss(pos_weight=neg/pos) or class weights in CE.
  3. Focal loss: down-weights easy examples so training focuses on hard ones: FL = −α(1−p)γ log p, with γ≈2.
  4. Resampling: undersample the majority class or oversample the minority (balanced batch sampler). Re-calibrate the probabilities afterwards.
  5. Threshold tuning: choose the decision threshold on validation data from business costs (e.g. the cost of a missed fraud vs. the cost of blocking a good customer).

Hyperparameter tuning order

Tune in this order. Each item matters more than the ones below it.

  1. Learning rate (log scale: 1e-5 → 1e-1)
  2. Batch size and number of epochs (with early stopping)
  3. Model capacity: layers and width
  4. Regularisation: dropout, weight decay
  5. Optimizer betas, schedule details

Use random search or Bayesian optimisation (Optuna), not grid search. Random search explores the important dimensions better.

The model-improvement playbook

✅ Say this in interviews: "How would you improve your model?"
  1. Check the data before the model. Label noise, leakage, train/serve skew, and whether the validation split mimics production (time-based split for anything temporal).
  2. Overfit one batch. If the model can't drive the loss to ~0 on 32 samples, it's a bug, not a modelling problem.
  3. Establish a baseline (GBDT / logistic regression / pretrained model) and compute the human or "Bayes" error if you can.
  4. Read the bias/variance gap. High train error means underfitting: bigger model, train longer, better features. Large train/val gap means overfitting: more data, augmentation, regularisation, smaller model.
  5. Do error analysis. Slice errors by segment (new customers, a merchant category, a device type). Fixing the worst slice beats tuning hyperparameters.
  6. Use transfer learning or pretraining for images and text, and self-supervised pretraining on unlabelled transactions.
  7. Ensemble a few seeds or architectures (often the DL model + GBDT), then calibrate and tune the threshold.

Debugging checklist (loss not decreasing / NaN)

Loss is NaN or inf

LR too high · log(0) in a custom loss · no input normalisation · exploding gradients, so add clip_grad_norm_(params, 1.0) · fp16 overflow, so use a GradScaler.

Loss is flat

LR too low or too high · forgot zero_grad · wrong loss/activation combination (softmax + CE) · labels shuffled separately from inputs · dead ReLUs · frozen layers.

Val much worse than train

Overfitting · distribution shift between splits · leakage in train only · forgot model.eval().

Val better than train

Dropout and augmentation are only active in training (normal) · train loss is averaged over the epoch while val is measured at the end · val set is too easy.

Interview Q&A

Your validation loss starts increasing after epoch 5 while training loss keeps falling. What do you do?

That's overfitting. In order: early-stop at the best checkpoint, add regularisation (dropout, weight decay, augmentation), get more or cleaner data, reduce capacity, and use transfer learning. Also check the validation split mirrors production (e.g. time-based).

Adam vs SGD with momentum?

Adam adapts per-parameter step sizes, converges fast and needs little tuning, so it's the default, especially for transformers and sparse embeddings (use AdamW). Well-tuned SGD+momentum can generalise slightly better on vision tasks. In practice: AdamW first; try SGD for CNNs if you have the budget to tune it.

Why does AdamW exist if Adam already supports weight_decay?

In Adam, L2 decay is added to the gradient and then divided by √v, so heavily-updated weights get less regularisation, which isn't what you want. AdamW applies the decay directly to the weights, separately from the adaptive step, so it regularises uniformly. It gives better generalisation.

BatchNorm vs LayerNorm. Why do transformers use LayerNorm?

BatchNorm computes statistics across the batch, which is unstable with small or variable batches and variable-length sequences, and it behaves differently in training and inference. LayerNorm normalises each token's features independently, so it doesn't depend on the batch and behaves the same in training and inference.

How does dropout behave at train vs test time?

During training, each unit is zeroed with probability p and the survivors are scaled by 1/(1−p) ("inverted dropout"). At test time nothing is dropped and no scaling is needed because the expected activation already matches. It approximates averaging an ensemble of sub-networks.

What is gradient clipping and when do you need it?

Rescaling the gradient vector when its norm exceeds a threshold (e.g. 1.0). It prevents exploding gradients, which are common in RNNs, transformers and very deep nets. Clipping by norm keeps the direction; clipping by value doesn't.

How do you choose batch size?

As large as fits in GPU memory for throughput, within reason. Large batches give less noisy gradients and may generalise worse unless you scale the LR and use warm-up. Small batches add regularising noise but are slower. 32–256 is typical; use gradient accumulation to simulate larger batches.

Fraud is 0.1% of your data. Walk through your approach.

Use a time-based split. Choose metrics like PR-AUC or recall at a fixed false-positive rate, or expected cost. Start with a GBDT baseline. In the network, use a weighted BCE or focal loss, or balanced mini-batches. Calibrate the probabilities (Platt/isotonic) and pick the threshold from the cost matrix. Monitor drift because fraud patterns adapt.
