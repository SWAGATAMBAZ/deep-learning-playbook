GRU in depth (and LSTM vs GRU)

The GRU (Cho et al., 2014) keeps the LSTM's core trick, gated additive memory, but folds it into one state and two gates. It has about 25% fewer parameters than an LSTM of the same size, trains faster, and performs on par in most real-world tasks. That's why it's often the first recurrent model to try.

Intuition: a dimmer switch between old and new

🧒 In plain English

A GRU keeps one memory vector. At every step it asks two questions. Reset gate r: "When drafting a new memory, how much of the past should I look at?" (r ≈ 0 means start fresh, as at the start of a new session). Update gate z: "Should I keep the old memory or replace it with the draft?" It works like a dimmer that blends old and new. The LSTM's separate forget and input gates are merged into this one dimmer: whatever fraction you keep, you don't write.

gate 1

Update gate zt

Blend weight between the old state and the candidate. It plays the role of both the LSTM's forget gate and input gate (they're coupled: keep z, write 1 − z).

gate 2

Reset gate rt

How much of ht−1 to use when computing the candidate. Lets the unit ignore irrelevant history for the new proposal.

proposal

Candidate nt (h̃t)

New content computed from the input and the reset-filtered past, squashed by tanh.

no cell state

Single state ht

Memory and output are the same vector, and there's no output gate. Simpler and cheaper, with slightly less control over what is exposed.

The equations

📐 One GRU step (PyTorch convention)

rt = σ(Wr xt + Ur ht−1 + br)   reset gate
zt = σ(Wz xt + Uz ht−1 + bz)   update gate
nt = tanh(Wn xt + bin + rt ⊙ (Un ht−1 + bhn))   candidate
ht = (1 − zt) ⊙ nt + zt ⊙ ht−1

In this convention z ≈ 1 keeps the old state and z ≈ 0 replaces it. Some textbooks swap z and 1 − z; it's the same model with the gate's meaning flipped, so state which convention you use in an interview. PyTorch packs the weights in the order r, z, n, and applies r after the hidden-side bias (the cuDNN variant). Cho et al.'s original applies r to ht−1 before the matrix multiply. Both work similarly.

Why gradients survive in a GRU

📐 The direct path
∂ht/∂ht−1 = diag(zt) + (terms through nt, rt, zt)

The interpolation ht = z⊙ht−1 + (1−z)⊙n gives a direct, gated, additive path from ht−1 to ht, just like the LSTM's cell path. Where the model learns z ≈ 1, information and gradient pass through many steps nearly unchanged. It's also a learned version of a residual (skip) connection through time.

🎯 The one-liner

"A GRU merges the LSTM's forget and input gates into a single update gate and drops the separate cell state and output gate. That's ~25% fewer parameters and faster, with similar accuracy on most tasks. I'd try a GRU first and switch to an LSTM if very long dependencies or validation results justify it."

Parameter count

📐 Formula
params per layer per direction = 3 × (I·H + H·H + 2H)

I = 32, H = 128, 1 layer → 3 × 20,736 = 62,208 (vs 82,944 for an LSTM and 20,736 for a vanilla RNN).

Variants and famous GRU systems

Bidirectional / stacked GRU

Same rules as LSTM: bidirectional for offline tagging, 1–3 layers, dropout between layers.

GRU4Rec (2016)

Session-based recommendation: a GRU reads the clicks in the current session and predicts the next item, trained with ranking losses (BPR/TOP1) and in-batch negatives. A classic e-commerce baseline before SASRec.

GRU-D (2018)

Handles irregular, missing time-series values (clinical data) by learning decays toward the mean based on the time since the last observation. Relevant to banking events with irregular gaps too.

Minimal / light gated units

Even simpler cells (MGU, a single forget gate; Li-GRU with ReLU for speech) trade a little accuracy for speed.

GRU encoder–decoder

The architecture where GRU was introduced (Cho et al. 2014, machine translation), later with Bahdanau attention.

DeepAR-style forecasting

Autoregressive RNN forecasters can use LSTM or GRU cells interchangeably; GRU is often faster with similar accuracy.

How to improve GRU performance

✅ Checklist
  1. Everything on the LSTM checklist applies: per-step features with time deltas, normalised numerics, embeddings for categoricals, packing, clipping, regularisation, pooling over outputs, combining with static features.
  2. Spend the saved compute: since a GRU is cheaper, try a wider hidden size or a second layer for the same latency.
  3. Irregular timing: add log(time since the last event) as an input, or use GRU-D-style decay for missing data.
  4. Session data (GRU4Rec style): use ranking losses with many sampled negatives, and session-parallel mini-batches.
  5. Compare honestly: GRU vs LSTM vs a small transformer vs GBDT on aggregates, with the same features and out-of-time validation, averaged over seeds (the differences are often within noise).

Interview Q&A

Explain the GRU's two gates.

The reset gate r decides how much of the previous state feeds into the candidate n. The update gate z blends: ht = z⊙ht−1 + (1−z)⊙nt (PyTorch convention), so z ≈ 1 keeps memory and z ≈ 0 overwrites it with the candidate.

How is a GRU different from an LSTM?

One state instead of two (no separate cell state), two gates instead of three (no output gate), and forget and input are coupled into one update gate. That gives ~25% fewer parameters and faster compute, with typically similar accuracy.

Why does a GRU avoid vanishing gradients?

The update equation contains a direct, gated linear path z⊙ht−1, so ∂ht/∂ht−1 includes diag(z). With z ≈ 1, gradients flow through many steps without repeated squashing, much like the LSTM cell path or a residual connection.

What does the reset gate let the model do that the update gate can't?

Compute a fresh candidate that ignores the past (r ≈ 0), e.g. at the start of a new session or topic, while the update gate still decides whether to adopt it. Without r, every candidate would be contaminated by the old state.

When would you pick an LSTM over a GRU?

When validation shows it's better, typically on very long dependencies or language modelling, or when you need independent control of keeping and writing (keep all old memory and also add new). Otherwise a GRU is cheaper, often as good, and a sensible first try.

Parameter count of a GRU layer with input 32, hidden 128?

3·(32·128 + 128·128 + 2·128) = 3·20,736 = 62,208 in PyTorch (two bias vectors).

How would you handle irregularly spaced events with a GRU?

Add time-since-previous-event (log-scaled) and calendar features as inputs. For missing measurements, use masks and GRU-D-style learned decay of the last observation toward the mean. Alternatively, use continuous-time models or time-aware transformers.
