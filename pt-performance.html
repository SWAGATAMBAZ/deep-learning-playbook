The optimisation order (cheapest wins first)

  1. Measure: time per step, GPU utilisation (nvidia-smi), the profiler trace. Never optimise blind.
  2. Fix the input pipeline: num_workers, pin_memory, pre-processed or cached data, GPU-side augmentation.
  3. Mixed precision (bf16 autocast) and TF32 matmuls: often 1.5–3× faster for free.
  4. Bigger batches up to the memory limit; channels_last for CNNs; fused optimizers.
  5. torch.compile: fuses kernels and cuts Python overhead.
  6. Memory tricks to fit more: gradient accumulation, activation checkpointing, 8-bit optimizers.
  7. Scale out: DDP across GPUs, FSDP2 when the model doesn't fit on one GPU.

Profiling: find the real bottleneck

🎯 Tooling note

The old TensorBoard profiler plugin is deprecated. Export a trace and open it in Perfetto (ui.perfetto.dev) or chrome://tracing. For multi-GPU analysis use Holistic Trace Analysis (HTA). Look for gaps on the GPU timeline: that's the GPU waiting for data or Python.

Mixed precision (AMP)

🧒 In plain English

Most of the maths in a network doesn't need 32-bit precision. Doing matrix multiplies in 16-bit roughly halves memory traffic and uses the GPU's tensor cores, while sensitive ops (softmax, losses, reductions) stay in 32-bit automatically. bfloat16 keeps fp32's range, so it just works. float16 has a small range, so tiny gradients underflow to zero unless you scale the loss up first (GradScaler).

torch.compile

  • model = torch.compile(model) captures the Python into graphs (TorchDynamo) and generates fused kernels (TorchInductor/Triton). The first call is slow (compiling); later calls are faster.
  • Modes: default; "reduce-overhead" (CUDA graphs, good for small batches and inference); "max-autotune" (longest compile, fastest kernels).
  • Graph breaks (data-dependent Python, .item(), unsupported ops) reduce the gains. Find them with TORCH_LOGS="graph_breaks". Changing input shapes triggers recompiles; use dynamic=True or pad to fixed sizes.
  • Typical speed-ups: 1.3–2× in training on modern GPUs. Always benchmark your own model.

📐 The 16-bytes-per-parameter rule

Adam training in fp32 (or AMP with fp32 master weights) needs about 4 (weights) + 4 (grads) + 8 (Adam m, v) = 16 bytes per parameter before activations. A 1B-parameter model needs ~16 GB just for that, which is why fine-tuning big models needs LoRA, sharding or 8-bit optimizers.

The CUDA out-of-memory playbook

  1. Make sure you aren't holding graphs: loss.item() for logging, torch.no_grad() in eval, and no lists of tensors that require grad.
  2. Halve the batch size and use gradient accumulation to keep the effective batch.
  3. bf16 autocast: activations take roughly half the memory.
  4. Activation checkpointing (torch.utils.checkpoint): recompute activations in backward instead of storing them. Large memory savings for ~20–30% extra compute.
  5. Shorter sequences or smaller images; truncate or tile.
  6. 8-bit optimizer, or freeze layers / LoRA.
  7. Shard across GPUs with FSDP2, or CPU offload as a last resort.
  8. Inspect: torch.cuda.max_memory_allocated(), torch.cuda.memory_summary(), and memory snapshots viewed at pytorch.org/memory_viz.

Interview Q&A

bf16 vs fp16: which and why?

bf16 has the same 8-bit exponent as fp32 (same range) with fewer mantissa bits, so gradients rarely overflow or underflow and no loss scaling is needed. fp16 has more precision but a tiny range, so it needs GradScaler. Use bf16 on Ampere and newer GPUs; fp16 + scaler on older ones (T4, V100).

Why must you call torch.cuda.synchronize() when timing?

CUDA kernels launch asynchronously; Python returns before the GPU finishes. Without synchronising you measure launch time, not compute time. Also warm up first.

DDP vs FSDP?

DDP replicates the full model on each GPU and averages gradients. It's simple and fastest when the model fits. FSDP shards parameters, gradients and optimizer state across GPUs, gathering layers on demand. It costs more communication but fits much bigger models.

How much GPU memory does fine-tuning a 7B model with AdamW need?

Full fine-tuning: ~16 bytes/param × 7B ≈ 112 GB before activations, so you need multiple GPUs with FSDP. With LoRA on a frozen bf16 base: ~14 GB of weights plus small adapter states and activations, so one 24–40 GB GPU. With QLoRA (4-bit base): ~4–5 GB of weights, so even 16 GB GPUs can work.

What is activation checkpointing?

Instead of storing every layer's activations for backward, store only some and recompute the rest during the backward pass. It trades extra compute (~20–30%) for a large memory reduction, letting you train deeper models or larger batches.

Training is slow and GPU utilisation is low. Steps?

Profile. If the GPU timeline has gaps: raise num_workers, use pin_memory + non_blocking, cache or pre-process data, move augmentation to the GPU, and remove per-step .item()/.cpu() syncs. Then use bigger batches, AMP and torch.compile.
